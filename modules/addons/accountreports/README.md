# Account Reports (WHMCS Addon Module)

Developed exclusively by **[Ucartz](https://www.ucartz.com)** and released as open source under the
[MIT License](LICENSE).

Lets logged-in clients view and export (CSV/PDF) a report of their invoices joined against the
services those invoices billed for, with a global default and a per-customer override controlling
whether the feature is available at all.

Target: WHMCS 8.x/latest, PHP 8.x/latest. Client area theme "lagom" in mind, but the module itself
is theme-agnostic — see [Theme overrides](#theme-overrides).

## Use case

Stock WHMCS has no way for a customer to get a consolidated report of their invoices and the
services those invoices were billed for — the client area shows invoices one at a time
(**Billing > My Invoices**) and services one at a time (**Services > My Services**), with no
combined, filterable, downloadable view tying the two together, whether for their currently active
services or ones they've had previously. A customer (or their accounts team) who wants "everything
we were billed for, and what it was for, over a given period" as a spreadsheet or PDF has no way to
get that on their own — normally that means opening a support ticket and asking staff to pull it
manually. This module adds exactly that: a self-service report joining invoices to the services they
billed for, filterable by date range/service/invoice status, exportable as CSV or PDF, directly from
the client area.

## Features

**Client area**
- A "Reports" item is added to the client area navigation, but only for customers the feature is
  actually enabled for (see [Per-customer access control](#per-customer-access-control)).
- The report page doesn't auto-load a customer's full history on landing — it prompts them to
  filter first (due date range, service, invoice status), then shows results.
- Results are paginated (25/page by default, capped by admin config), with a "blocks of 20 pages +
  jump to last page" pagination widget so a customer with a long history doesn't get an unusable
  wall of page links.
- **Export CSV** and **Export PDF** buttons, honoring the current filters, each independently
  toggleable by the admin (see Configuration below) and enforced server-side either way.
- If Reports is disabled for a customer, or an export fails, they see a friendly message rendered
  inside the theme's normal page layout (header/nav/footer intact) — never a bare, unstyled error
  page.
- Filter/search layout uses the module's own responsive CSS (not the active theme's Bootstrap grid
  classes), so it renders correctly regardless of which client area theme is active.

**Admin (Setup > Addon Modules > Account Reports > Configure)**
- Module-wide settings: default enablement, max export rows, which report types/columns are shown,
  which export formats are allowed, a max filter date range, and an optional product-group
  restriction (see [Configuration](#configuration)).
- A live summary of how many customers are individually enabled/disabled vs. using the account-wide
  default, so you can see the current access picture at a glance.
- A searchable (by name/email/client ID), status-filterable (Active/Inactive/Closed) customer list
  with a per-row Enable/Disable/Reset-to-default action.
- Bulk actions — **Enable For All Customers**, **Disable For All Customers**, **Reset All To
  Default** — each behind a confirmation dialog, processed in batches so it stays fast with many
  thousands of clients.
- The same Enable/Disable toggle is also available directly on each client's own admin profile page
  (**Clients > [a client] > Summary**), without needing to go find them in the Configure page's list.

## Directory structure

Every file below is required at runtime — nothing dev-only ships in this package. This includes
`composer.json` and `vendor/` (bundled Dompdf) — see [Export implementation notes](#export-implementation-notes)
for why.

```
modules/addons/accountreports/
├── accountreports.php          Module glue: config/activate/deactivate/upgrade/output/clientarea
├── hooks.php                   ClientAreaPrimaryNavbar injection, admin client-profile widget, cleanup
├── README.md
├── composer.json               Pins dompdf/dompdf -- required at runtime, must be uploaded
├── vendor/                     Generated by `composer install --no-dev` -- required at runtime, must be uploaded
├── lib/
│   ├── helpers.php              Procedural helpers shared by accountreports.php AND hooks.php
│   │                            (see the note in that file on why it's separate from the main module file)
│   ├── Reports/
│   │   └── InvoiceServiceReportService.php   Query/data logic
│   ├── Services/
│   │   ├── ClientAccessService.php           Per-customer override table + effective-enabled logic
│   │   └── ConfigService.php                 Typed access to the addon's config() values
│   ├── Export/
│   │   ├── CsvExporter.php                   Streaming CSV (fputcsv)
│   │   └── PdfExporter.php                   PDF via Dompdf (bundled with this module)
│   └── Security/
│       └── CsrfGuard.php                     CSRF check for this module's own POST actions
├── templates/
│   ├── client/                  Default client-area templates (theme-overridable, see below)
│   │   ├── reports.tpl
│   │   ├── disabled.tpl         Also used for export-failure and access-denied messages
│   │   └── reports_pdf.tpl      Bare HTML fed to Dompdf — not part of theme resolution
│   └── admin/                   Admin-only fragments (not theme-resolved; rendered directly)
│       ├── customers.tpl        Search/filter/bulk-actions/per-customer list (Configure page)
│       └── client_profile_widget.tpl
├── lang/
│   └── english.php              $_ADDONLANG strings used by templates/client/*.tpl
└── assets/
    ├── css/accountreports.css   Theme-independent responsive layout for the filter forms
    └── js/accountreports.js
```

There is no root-level `admin/` folder — WHMCS addon modules are entirely self-contained under
`modules/addons/<module>/`. When an admin opens **Setup > Addon Modules**, WHMCS's own
`admin/addonmodules.php` calls this module's `accountreports_output()` function and echoes what it
returns; you never place module files inside WHMCS's own `/admin/` directory.

There is also no `sql/` install script. `mod_accountreports_customer_settings` is created
programmatically by `ClientAccessService::migrate()` inside `accountreports_activate()` — see
[Database](#database).

## Installation — where to upload

1. Upload the **entire** `accountreports/` folder, exactly as-is (including `vendor/`), into your
   WHMCS install's `modules/addons/` directory, so the main module file ends up at:
   ```
   <your-whmcs-root>/modules/addons/accountreports/accountreports.php
   ```
   For example, on a typical cPanel layout this might be:
   ```
   /home/youruser/public_html/modules/addons/accountreports/accountreports.php
   ```
   (or `/home/youruser/public_html/clients/modules/addons/accountreports/accountreports.php` if
   your WHMCS install itself lives in a `clients/` subfolder, as is common).
2. In the WHMCS admin area, go to **Setup > Addon Modules**, find **Account Reports**, and click
   **Activate**. This creates the `mod_accountreports_customer_settings` database table — no manual
   SQL step needed.
3. Click **Configure** and set the module-wide options (see [Configuration](#configuration)). Click
   **Save Changes** — nothing is persisted to the database until you do, even if a setting shows a
   pre-checked default on first load.
4. Decide on an access policy (see [Per-customer access control](#per-customer-access-control)) —
   either open to everyone by default, or closed by default with specific customers opted in.

No other files need to be uploaded anywhere else, and nothing needs to be placed in WHMCS's own
`/admin/` directory (see [Directory structure](#directory-structure) for why).

## Configuration

Set on **Setup > Addon Modules > Account Reports > Configure**:

| Setting | Purpose |
|---|---|
| Enable Reports For New Customers By Default | **Off by default** on a fresh install. The fallback used for any customer with no explicit per-customer override — see [Per-customer access control](#per-customer-access-control). |
| Max Rows Per Report Export | Ceiling on rows per page and per export; hard-capped at 1000 regardless of the value entered. |
| Enable Invoice Reports / Enable Service Reports | Which column groups are shown/exported. At least one should stay on, or the client area page shows a "no report types enabled" message. |
| Allow CSV Export / Allow PDF Export | Enforced server-side on every export request — see [Security](#security). Uncheck "Allow PDF Export" if you'd rather not carry the bundled Dompdf library at all; CSV works independently. |
| Max Filter Date Range (days) | Largest span allowed between the due-date "from" and "to" filters; `0` = unlimited. |
| Restrict To Product Group IDs | Optional comma-separated `tblproducts.gid` values to scope reported services to specific product groups. |
| Preserve Per-Customer Settings On Deactivate | If off, deactivating the module also drops the override table — see [Database](#database). |

Whether the module is active at all is controlled the standard WHMCS way, via **Activate**/**Deactivate**
on the Addon Modules list — there's no separate "master switch" setting.

## Per-customer access control

Effective enablement for a client is resolved as:

```
effective_enabled = per-customer override (if a row exists in
                     mod_accountreports_customer_settings) else the
                     "Enable Reports For New Customers By Default" config value
```

This logic lives in one place, `ClientAccessService::isEnabledForClient()`, and is used consistently
by the client-area nav injection, the client-area page controller, and the admin UI, so all three
can never disagree.

**Two common policies:**

- **Open to everyone, with exceptions**: leave "Enable Reports For New Customers By Default" on,
  and individually **Disable** the specific customers who shouldn't have it.
- **Closed by default, opt-in per customer** (the fresh-install default): turn "Enable Reports For
  New Customers By Default" off and save, then individually **Enable** just the specific customers
  who should have access, using the search box on the Configure page. Turning the default off
  covers every customer automatically — present and future signups alike — without needing to
  touch existing customers at all.

**Managing overrides:**
- The **Manage Customers** panel on the Configure page: search by name/email/client ID, filter by
  client status (Active/Inactive/Closed), and Enable/Disable/Reset-to-default per row. A summary box
  at the top shows how many customers are currently individually enabled/disabled vs. on the default.
- The **Account Reports Access** panel injected directly onto each client's own admin profile page
  (**Clients > [a client] > Summary**) — the same toggle, without leaving that page.
- **Bulk actions** (Enable For All / Disable For All / Reset All To Default) on the Configure page,
  for applying a setting to every customer at once — each behind a confirmation dialog, processed in
  batches of 500 (`ClientAccessService::bulkSetOverrideForAllClients()` / `clearAllOverrides()`) so
  it stays fast even with many thousands of clients. Note bulk actions only affect customers that
  exist at the moment you click — for a policy that also covers *future* signups, use the
  account-wide default instead (see policies above).

## Client area experience

`accountreports_clientarea()` returns `'templatefile' => 'client/reports'` for the report page and
`'client/disabled'` for every "can't show the report" case — feature disabled for this customer, no
report types enabled, or an export request that failed (invalid CSRF token, no format selected,
format disabled by admin). All of these render inside WHMCS's normal themed page layout with a
plain-language message, never a raw error page.

On landing (no filters submitted yet), the page shows a prompt instead of the customer's full
history. Submitting the filter form (even with all fields blank) runs the query and shows results,
paginated in blocks of 20 pages with a jump-to-last-page link for long histories.

## Theme overrides

WHMCS resolves an addon's client-area `templatefile` by first checking the **active theme's**
subfolder inside the module's own `templates/` directory, falling back to the module's own default
alongside it:

1. `modules/addons/accountreports/templates/<active_theme>/client/reports.tpl` (theme override, if present)
2. `modules/addons/accountreports/templates/client/reports.tpl` (this module's default — used otherwise)

So to give the report page a Lagom-specific look without touching this module's code, a theme
developer adds:

```
modules/addons/accountreports/templates/lagom/client/reports.tpl
```

and WHMCS picks that up automatically. The module itself never assumes anything about the active
theme's markup, CSS classes, or asset locations — see the CSS note in [Directory structure](#directory-structure).

## Security

- Every query is scoped with the client ID pulled from `$_SESSION['uid']` — WHMCS's own client-area
  session identity, used consistently by both `accountreports_clientarea()` and `hooks.php`. It is
  never taken from request input. Admin impersonation is handled for free: WHMCS points
  `$_SESSION['uid']` at the impersonated client for the duration of the session, so the nav hook and
  page controller are automatically scoped to the impersonated client, not the admin.
- All data access goes through Capsule's query builder (`lib/Reports/InvoiceServiceReportService.php`,
  `lib/Services/ClientAccessService.php`) — no string-concatenated SQL anywhere in the module.
- The export POST action and the admin toggle POST actions both require a valid CSRF token
  (`lib/Security/CsrfGuard.php`). This token is minted and validated entirely by the module itself
  (`$_SESSION['accountreports_csrf_token']`, `hash_equals()`) — it does not rely on any WHMCS-internal
  session key (see [Implementation notes for maintainers](#implementation-notes-for-maintainers)).
- `ConfigService::isExportFormatAllowed()` is checked inside `accountreports_handle_export()` itself,
  so a hand-crafted `format=pdf` request is rejected even if the corresponding button is hidden in
  the UI because PDF export is disabled in config.
- Both the paginated client-area report and CSV/PDF exports are hard-capped by
  `InvoiceServiceReportService::HARD_MAX_PER_PAGE` (1000) regardless of the admin's configured "Max
  Rows" value, so the report page/exports can't be used to dump an unbounded result set.

## Export implementation notes

- **CSV** (`lib/Export/CsvExporter.php`) writes rows with `fputcsv()` directly to `php://output` as
  they're iterated, with a periodic `flush()` — it never assembles the file as an in-memory string.
- **PDF** (`lib/Export/PdfExporter.php`) uses **Dompdf**, bundled with this module (`composer.json` +
  `vendor/` in the module root) rather than assumed from WHMCS's own copy — see
  [Implementation notes for maintainers](#implementation-notes-for-maintainers) for why. Adds about
  13MB to the module (mostly Dompdf's own font files); no runtime performance difference from using
  a shared copy, and no server-load concern — PDF generation is only triggered by an explicit
  customer action, never automatically, and rows are already hard-capped. The PDF body is rendered
  from `templates/client/reports_pdf.tpl`, a standalone HTML document (not run through WHMCS's
  theme-wrapping template resolution, since a PDF shouldn't include the theme's nav/header/footer).
- **If you'd rather not carry Dompdf at all**: uncheck "Allow PDF Export" in Configuration. CSV
  export is unaffected — no code changes needed either way.

## Database

`mod_accountreports_customer_settings` (`client_id`, `enabled`, `created_at`, `updated_at`) is
created via `ClientAccessService::migrate()` inside `accountreports_activate()`, using Capsule's
Schema builder. No `.sql` file ships with the module — a standalone `.sql` file would only duplicate
that and, being non-PHP, can't carry a `WHMCS`-constant guard; if left in a web-accessible module
folder, a direct request to its URL would just serve your schema back as plain text.

On deactivation, `accountreports_deactivate()` drops that table **only if** "Preserve Per-Customer
Settings On Deactivate" is off; by default (on) the table and all overrides survive deactivation, so
re-activating later doesn't lose admin-configured per-customer state. No foreign key is declared
against `tblclients` (third-party modules shouldn't attach FKs to WHMCS core tables); orphaned rows
for deleted clients are instead cleaned up via the `ClientDelete` hook in `hooks.php`.

## Implementation notes for maintainers

A running list of non-obvious things this module got wrong once and fixed, kept here so a future
change doesn't reintroduce the same bug:

- **`hooks.php` must never `require`/`include` `accountreports.php`.** WHMCS's own core module
  loader already loads that file directly (via a plain, non-`_once` include) whenever it needs to
  call one of its standard functions — e.g. rendering the Addon Modules list or Configure page.
  `hooks.php` runs on every request too; if it also required `accountreports.php`, any admin page
  where both loaders ran in the same request fataled with `Cannot redeclare accountreports_config()`.
  Shared logic `hooks.php` needs lives in `lib/helpers.php` instead, required independently by both
  files, and every function in `accountreports.php` is additionally wrapped in a `function_exists()`
  guard as a second line of defense.
- **`accountreports_clientarea($vars)`'s `$vars` does not contain a `clientsdetails` key.** WHMCS
  only passes `modulelink`/`version`/the module's own config field values/`_lang` into an addon
  module's `_clientarea()` function, never the logged-in client's identity. Use `$_SESSION['uid']`
  instead (see [Security](#security)).
- **WHMCS does not expose its own core CSRF token to third-party modules.** There's no documented,
  supported `$_SESSION` key or helper for this — confirmed against WHMCS's own community/feature-request
  history (a long-standing open request literally asks WHMCS to add it). `CsrfGuard` mints and
  validates its own token instead, under its own session key.
- **Don't assume WHMCS's bundled Dompdf is autoload-accessible to module code.** It genuinely does
  ship with WHMCS (for invoice/quote PDFs), but isn't reliably reachable from third-party code on
  every install. `PdfExporter` bundles its own copy and only uses it as a fallback (`class_exists()`
  check first) — see [Export implementation notes](#export-implementation-notes).
- **Don't disable a form's just-clicked submit button synchronously inside its own `submit` event
  handler.** Some browsers (notably Safari) drop that button's `name=value` pair from the submitted
  form data entirely when this happens, which silently broke CSV/PDF export regardless of server
  config. `assets/js/accountreports.js` defers the disable via `setTimeout(fn, 0)` instead.
- **Compute pagination/block math in PHP, not as arithmetic chained with modifiers inside a Smarty
  `.tpl`.** An attempt at `{assign value=($page-1)/$blockSize|floor}` silently bound the `|floor`
  modifier to `$blockSize` alone rather than the whole division, producing wrong block boundaries.
  `accountreports_add_pagination_block()` computes this in testable PHP instead.
- **Always fully populate an array passed to a Smarty template**, even keys with no value for this
  request (e.g. `$filters['service_id'] = ''` rather than omitting the key). Smarty's `|default`
  modifier does not suppress the PHP "Undefined array key" warning that array access itself throws
  on a genuinely missing key.
- Opening `accountreports.php` outside of a WHMCS install (a standalone linter/IDE with no WHMCS
  source indexed) will flag `ROOTDIR`, `Smarty`, and `Illuminate\Database\Capsule\Manager` as
  undefined. Expected — all three are provided by WHMCS's own `init.php` bootstrap at runtime, not
  by this module.
- The original task description mentioned `AdminClientProfileTabsSummary` as a possible hook for the
  client-profile toggle widget. That name isn't in WHMCS's documented hook point registry, so
  `hooks.php` uses `AdminAreaClientSummaryOutput` instead — the long-standing, documented hook for
  injecting output directly into a client's admin summary page.
